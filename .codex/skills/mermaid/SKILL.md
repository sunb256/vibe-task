# Mermaid

## 目的

日本語の仕様書・設計書で使う Mermaid 図を作成する。

この skill では次を優先する。
- 日本語で読みやすい
- Markdown にそのまま貼れる
- レビューしやすい
- 修正しやすい
- 必要以上に複雑にしない

対象は次の 2 種類のみ。
- `flowchart`
- `sequenceDiagram`

## 出力

出力は`docs/` 配下に出力する。
特にしていなければ、以下のファイル名とする

`docs/marmeid.md` とする

## 使う場面

次のような依頼で使う。
- 文章や箇条書きから flowchart を作る
- API やシステム連携の説明から sequenceDiagram を作る
- 既存の Mermaid を仕様書向けに整理する
- 業務フロー、申請フロー、承認フローを図にする
- 画面、API、DB の流れを図にする
- Markdown に貼れる Mermaid に変換する

使わない場面:
- 画像ファイルの図が欲しい
- Mermaid 以外の図表形式が欲しい
- ER 図や状態遷移図などが欲しい
- 装飾やビジュアル重視の図が欲しい

## 基本方針

- 図の種類が未指定なら内容から `flowchart` か `sequenceDiagram` を選ぶ
- 明記されている要素は落とさない
- 深い実装詳細は勝手に足しすぎない
- 曖昧な点は推測を最小限にする
- 既存 Mermaid の修正では不要な全面書き換えを避ける
- 仕様書に必要な範囲へ絞る
- 適切な改行をする(flowchartの改行は\n、sequenceDiagramの改行は<br/>)

## 図の選び方

### flowchart
次のような内容で使う。
- 業務フロー
- 申請から承認までの流れ
- 条件分岐を含む処理手順
- 入力、確認、登録、通知の流れ

原則:
- `flowchart TD`
- 上から下へ読む構成
- ノードは短い動作または判定
- 分岐は必要最小限
- 複雑なら分割を優先

### sequenceDiagram
次のような内容で使う。
- API 呼び出し順
- 画面、API、DB のやり取り
- サービス間連携
- 認証・認可処理
- リクエストとレスポンスの時系列

原則:
- 参加者名は役割が分かる名前にする
- 時系列順に並べる
- 意味のあるメッセージだけを書く
- 細かすぎる内部処理は省略してよい

迷った場合:
- 手順や分岐の説明が主目的なら `flowchart`
- 参加者間の時系列のやり取りが主目的なら `sequenceDiagram`

## 日本語運用ルール

- 表示ラベルは原則日本語
- ユーザーが使った用語を優先する
- 同じ意味の語を勝手に言い換えすぎない
- ノード名やメッセージ名は短くする
- 1 ノード 1 意味を基本にする
- 長文をノードに詰め込みすぎない

良い例:
- `申請内容を入力`
- `入力内容を確認`
- `申請を登録`
- `認証結果を返却`

避けたい例:
- `ユーザーが必要事項を入力して確認ボタンを押下する`
- `システム内部で各種整合性確認処理を実施する`

## 既存 Mermaid の修正

既存の Mermaid がある場合は次の順で対応する。
1. 構文の不自然さを直す
2. 読みにくさを直す
3. 依頼された変更を反映する

修正時は:
- 図の種類を原則維持する
- 重要なノードや参加者を勝手に消さない
- 用語をむやみに変えない
- 差分が追いやすい形を優先する

## 出力ルール

原則として次の形で返す。

### 図

必要な場合だけ補足を書く。

* 図の対象範囲
* 前提
* 分割した方がよい場合の提案


## 禁止事項

* 明らかに壊れた Mermaid を返さない
* 根拠のない詳細を勝手に追加しない
* 過剰に巨大な図を 1 つに押し込まない
* 業務フローと通信順序を無理に混在させない
* 重要な要素を黙って削らない

## 完了条件

* ユーザーの意図に合う図になっている
* 仕様書に貼れる Mermaid になっている
* 日本語として自然である
* レビューで読みやすい
* 必要以上に作り込みすぎていない
